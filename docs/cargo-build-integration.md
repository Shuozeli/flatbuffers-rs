# Cargo Build Integration

`flatc-rs-build` generates Rust code from FlatBuffers schemas inside Cargo
build scripts. It uses Cargo's native freshness model rather than maintaining a
second hidden schema cache.

## Minimal Integration

Add the generated-code runtime and build helper:

```toml
[dependencies]
flatbuffers = "25.12.19"

[build-dependencies]
flatc-rs-build = { git = "https://github.com/Shuozeli/flatbuffers-rs.git", rev = "<reviewed-revision>" }
```

Generate code in `build.rs`:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    flatc_rs_build::Builder::new()
        .schema("schemas/game.fbs")
        .include_dir("schemas")
        .gen_all()
        .compile()?;
    Ok(())
}
```

Include the output from Rust source:

```rust
include!(concat!(env!("OUT_DIR"), "/game_generated.rs"));
```

Generated files belong in `OUT_DIR`. Build scripts should not modify checked-in
source files or files inside dependency package directories.

## Schema and Output Boundaries

Each path passed to `schema()` or `schemas()` is a direct root and produces one
`{stem}_generated.rs` file. The compiler resolves each root against only its
transitive include closure, so metadata and declarations from independent roots
cannot leak into one another.

Without `gen_all()`, an output contains declarations from its direct root only.
This matches the CLI default and is appropriate when included schemas are also
direct inputs with their own generated modules:

```rust
flatc_rs_build::Builder::new()
    .schemas([
        "schemas/common.fbs",
        "schemas/inventory.fbs",
        "schemas/game.fbs",
    ])
    .include_dir("schemas")
    .compile()?;
```

With `gen_all()`, every output also contains declarations from that root's
transitive includes. This is convenient for a single application root. Avoid
using `gen_all()` on several overlapping roots unless duplicated generated
declarations are intentional.

## Incremental Contract

The helper exposes the compiler's resolved source set and emits one directive
for every canonical path:

```text
cargo::rerun-if-changed=/workspace/schemas/common.fbs
cargo::rerun-if-changed=/workspace/schemas/game.fbs
```

It can also track explicit environment inputs:

```rust
flatc_rs_build::Builder::new()
    .schema("schemas/game.fbs")
    .rerun_if_env_changed("MY_FLATC_PROFILE")
    .compile()?;
```

Expected behavior:

| Change | Build script | FBS generation | Generated file write |
|---|---|---|---|
| Nothing changes | Skipped by Cargo | Skipped | Skipped |
| Direct FBS mtime changes | Runs | Runs | Only if bytes differ |
| Transitive include mtime changes | Runs | Runs | Only if bytes differ |
| `build.rs` or build dependency changes | Runs | Runs | Only if bytes differ |
| Tracked environment value changes | Runs | Runs | Only if bytes differ |

Cargo currently evaluates build-script file inputs using mtimes. If a schema is
only touched, Cargo reruns the build script even when its contents are unchanged.
The helper prevents an identical generated file from being rewritten, but Cargo
may still invoke `rustc` for the current crate after a dirty build script. This
is a Cargo boundary, not a persistent compiler cache.

## Supported Rust Generation Options

The builder exposes the Rust options supported by the compiler:

```rust
flatc_rs_build::Builder::new()
    .schema("schemas/game.fbs")
    .include_dir("schemas")
    .gen_all()
    .gen_object_api()
    .gen_name_strings()
    .rust_serialize()
    .no_leak_private()
    .rust_pluggable_buffer()
    .filename_suffix("_fb")
    .compile()?;
```

Generated code may require corresponding runtime dependencies. For example,
`rust_serialize()` requires serde and `rust_pluggable_buffer()` requires
`flatc-rs-runtime` in the consuming crate.

## Programmatic Results

`compile()` returns `BuildOutput`:

- `generated_files`: every expected direct-root output;
- `updated_files`: outputs whose generated bytes changed;
- `source_files`: canonical direct and transitive FBS inputs watched by Cargo.

`compile_with_writer()` writes Cargo directives to a supplied writer. It is
intended for deterministic tests and alternate build-system adapters.

## Errors

The build fails immediately for:

- missing, malformed, cyclic, or escaping includes;
- parser and semantic errors;
- invalid resolved schemas or code generation failures;
- public types exposing private types when `no_leak_private()` is enabled;
- two direct inputs producing the same output filename;
- a missing `OUT_DIR` when no explicit `out_dir()` is configured.

## Test Coverage

Library integration tests cover dependency directives, unchanged output bytes,
transitive changes, multiple roots, custom suffixes, missing includes, private
leaks, and output collisions.

The Cargo E2E tests create real temporary consumer crates. The incremental test
runs three sequential `cargo check` commands:

1. Initial code generation and Rust compilation.
2. An unchanged build where Cargo must not rerun `build.rs`.
3. A transitive include change that must rerun generation and compile the new
   generated accessor.

Failure E2E coverage starts from a successful generated artifact, then verifies:

- a malformed transitive schema fails with its path and parse error;
- the last valid generated file remains byte-for-byte unchanged after failure;
- repairing the schema regenerates code and restores a successful build;
- deleting a transitive include reports the missing include without corrupting
  the last valid output;
- restoring the include recovers on the next Cargo invocation;
- a transitive include cycle reports the repeated schema, preserves the last
  valid output, and recovers after the cycle is removed;
- a path-traversing include is rejected even when its target exists, preserves
  the last valid output, and recovers after the include is removed;
- an include that resolves but cannot be read reports its path, preserves the
  last valid output, and recovers after the bad include is removed;
- an output path that cannot be read reports the read operation and regenerates
  after the invalid path is removed;
- an output directory that cannot be created reports the create operation while
  preserving the last valid Cargo output, then recovers when writable;
- an existing output that cannot be written reports the write operation without
  changing its bytes or mtime, then regenerates when writable;
- two direct schemas with the same stem fail with an explicit output collision.

### E2E Harness

The E2E suite is split into incremental, schema-failure, filesystem-failure,
output-failure, and configuration scenarios under `build/tests/cargo_e2e/`.
Consumer sources live in `build/tests/fixtures/`; the harness copies them into a
unique temporary project and generates the manifest with a path dependency on
the current `flatc-rs-build` checkout. Permission-based output directory and
write failures run on Unix; output read failures remain cross-platform.

Projects are isolated, but their nested Cargo commands share
`target/flatc-rs-build-e2e` so compiler and dependency artifacts are reused.
Set `FLATC_RS_E2E_ISOLATED_TARGET=1` to give every scenario a fresh target when
investigating cache interaction.

Generated-artifact checkpoints compare both bytes and a deterministic mtime.
This distinguishes preserving valid output from silently rewriting identical
bytes. A project is retained automatically when its test panics. Set
`FLATC_RS_E2E_KEEP=1` to retain successful projects as well; the harness prints
the retained directory to stderr.

Run the focused suite with:

```sh
cargo test -p flatc-rs-build --test cargo_e2e
```

Run all build-helper integration and E2E tests with
`cargo test -p flatc-rs-build --tests`.

Use `cargo build -vv` in a consumer project to inspect Cargo freshness reasons
and the emitted `rerun-if` directives when diagnosing unexpected rebuilds.
